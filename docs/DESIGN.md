# 设计与架构

> 本文记录界面实现、文件写操作与文件夹接管的设计取舍，面向开发者。

## 界面实现说明（依据设计稿）

设计稿是三个 HTML 原型：`file-manager.html`（主界面）、`file-manager-settings.html`（设置页，
原稿未随仓库发布，本仓库按自拟版式实现为标签内页面，见下文「设置页为什么是『位置』」）、
`app-icons.html`（应用图标四稿）。主界面按设计稿逐条落地，取值不再散落在各处：

- **设计令牌唯一来源**：`crates/views/src/tokens.rs`。设计稿用 OKLCH 表达颜色，
  这里实现了一整条 `OKLCH → OKLab → 线性 sRGB → HSL` 转换链，并适配 GPUI 的
  `Hsla.h` 取值是 **0..1**（不是 0..360）这一单位差异——
  单元测试直接断言 `oklch(55% 0.2 258) ≈ #076be3`，与设计稿公布的换算值一致。
  派生色（`accent-soft` 16%、`accent-line` 45%、`hover` 6%…）按设计稿语义取「原色 + 透明度」。
- **尺寸与响应式**：字号 11/12/13/15/17、圆角 6/10、控件 30px、
  标题栏 38 / 标签条 38 / 标签 32 / 地址栏 32 / 列表头 28 / 状态栏 26、
  侧边栏 238（折叠 48）、预览面板 306 全部集中在 `tokens::metrics`；
  断点 1240 / 1100 / 980 / 920 / 720 / 560 集中在 `tokens::breakpoints`，
  由 `fm-shell::layout::Viewport` 一次性判定「当前宽度下哪些控件存在」。
- **组件库主题同步**：地址栏与搜索框用的是 `gpui_component::Input`，
  它的描边 / 底色 / 圆角读组件库主题，因此 `fm-shell::shell::apply_component_theme`
  会把设计令牌里的关键色值同步过去，避免这一个控件与周围割裂。

## 设置页、会话与列宽的实现取舍

### 设置页为什么是「位置」而不是新窗口

设置页做成 `Location::Settings`，于是它自动获得三件东西：标签条里的一格、
`Ctrl+W` 与「重新打开关闭的标签页」、以及 `TabState` 的前进后退历史。
独立窗口则要另写一套窗口生命周期、主题同步与焦点归还，而这套代码只有一处消费者。

代价是所有 `match Location` 必须多一个分支——**这正是想要的**：
编译器会把每一处「这里该怎么处理一个位置」逼出来，包括内容区分派、
地址栏文案与状态栏统计。漏掉的地方是编译错误，而不是运行期的空列表。

配套的三条约束：

- `as_dir()` 对设置页返回 `None`，因此它**不可能**被送进 `FileSystem::scan`；
- 切到设置页时清空 `entries` 与 `filtered`，否则状态栏会继续显示上一个目录的条数；
- 命令条在设置页隐藏搜索、视图切换、排序、预览与「新建」——它们在那里没有作用对象，
  留一个点了没反应的按钮比让它消失更像故障。

### 会话持久化：存什么、不存什么

`%APPDATA%\pagefold\session.json`，与 `config.json` 分开：配置坏了只是外观回到默认，
会话坏了则可能启动到一个不存在的目录，两者不该互相连坐。

存：标签顺序、每个标签的完整历史与游标、视图模式、激活下标、格式版本。
不存：扫描结果、选中集、滚动位置、排序键、已关闭标签栈。
前四项重启后要么能重算、要么已失效（目录内容可能变了）；最后一项是「本次会话」的
操作记录，跨重启复活一个可重开的标签没有对应的用户动作。

写入是**同步**的（与 `Config::save` 同策略）：快照是 KB 级 JSON，而去抖异步写会引入
「关窗瞬间丢掉最后一次导航」这条只在特定时序下出现的边界。挂点只有两个——
`reload_inner`（导航/切标签/开关标签都经过它）与 `set_view_mode`；拖拽重排标签在
松开时补一次。

容错是「全有或全无」：任一份标签快照的历史为空或游标越界，整份会话被拒绝并回退到
单个默认标签，而不是留下一个半对半错的历史（`TabsState` 的不变量是「至少一个标签」）。
命令行给了位置时不读会话：那是用户此刻的明确意图。

### 列宽：把「可见性」与「宽度」拆开

`Columns::for_viewport` 原本同时决定「哪些列显示」与「每列多宽」。加入拖拽后这两件事
必须分开：

- 断点仍然只回答**在不在**（`Option<f32>` 的 `None`）；
- 用户的拖动偏好（`ColumnWidths`，三列各自 `Option<f32>`）只覆盖**可见列**的宽度；
- `ColumnWidths::fitted` 在内容区不够宽时按「大小 → 类型 → 日期」收敛，
  名称列保底 180px——把名称挤没，整张表就没用了。

三条实现细节：

1. 分隔线是**绝对定位**的 6px 竖条，压在列交界处。若做成 flex 子项，每个分隔线都会
   把数据列挤窄 6px，表头与数据行的列就对不上了。
2. 拖动位移挂在**内容区**的 `on_mouse_move` 上，不是分隔线自己：6px 宽的命中区，
   鼠标一离开细线就收不到后续事件，拖动会卡在半路。
3. 读取路径也夹一次（`ColumnWidths::clamped`）。配置是磁盘上的 JSON，可能被手工改过，
   只在写入时夹的话，一个手改的 `9999` 就能让名称列消失。

偏好写进 `config.json` 的 `detail_columns`，旧配置缺这个字段时全部回落断点默认值。

### 预览面板的「在列表中定位」

滚动能力（`ShellView::scroll_into_view`，含网格「下标 → 行号」的换算）早已存在，
缺的只是一个入口。这里新增 `RevealHandler`，由 shell 实现为 `reveal_selected`：
取 `selection.single()`（退化为 `cursor`）→ 设回焦点项 → 滚动。

按钮只在 `PreviewContent::Single` 下渲染：多选时「定位到哪一条」没有答案，
与其给一个语义含糊的按钮，不如不给。

## 外部世界怎么进入界面：一个 400ms 的轮询

目录变更（自动刷新）与重复启动转发来的位置（IPC）都是「低频、且没有现成回调」的事件。
两者都收敛到 `ShellView::ambient_tick`，由同一个 400ms 循环驱动。

**为什么是轮询而不是事件回调。** 平台层不该持有 `ShellView`——那是分层的第一步。
要做到「事件直接推给 UI」，就得把视图句柄塞进平台层，或者在平台上再包一层事件总线；
而这两种事件都只关心「有没有发生」，一个计数器（目录变更）与一个槽位（IPC）就够表达了。
400ms 对「外部新建了一个文件」这种人眼容忍度很高的事件完全够用，
代价是空闲时每 400ms 一次空转比较（一次原子读 + 一次加锁读）。

**目录监听的三条约束。**

1. *只监听当前目录这一层*（`bWatchSubtree = false`）：递归监听的代价随深度上升，
   而列表本身也只显示当前层；子目录的变化在用户进入时会以一次新扫描覆盖。
2. *事件只累加计数器*，绝不直接改 `entries`：否则「解压一个压缩包」会在几秒内
   触发上千次重绘，还会与分批扫描的 `generation` 校验互相打架。
3. *扫描在途时跳过本次刷新*：那一批数据落地时本来就是最新的，
   此刻再插一次刷新只会把当前扫描取消掉、白费 IO。

**自动刷新要给内联重命名让路。** 新建一个项目会在磁盘上产生一次变更，而
「建完立刻改名」的输入框正是在这一刻打开的：若 400ms 后照常刷新，列表会被清空重建，
输入框随之消失。更糟的是会话本身还活着——它锚在「第 N 项」上，而列表已经换了一份，
于是输入框不再渲染，`editing_input()` 却仍为真，**所有全局快捷键都被吞掉**，
表现为「按回车什么也没发生」。

因此有两条约定：

1. 自动刷新在重命名会话期间**让位**（不消费变更计数，结束后下一次轮询自然补上）；
2. 任何刷新（F5、写操作后）都**结束**该会话——与其留一个看不见却吃按键的会话，
   不如明确结束它。

另外，自己造成的变更会被主动消费掉（`refresh_after_write` 与 `finish_create` 都调用
`watcher.take_change()`）：那次变化紧接着就会被自己的重扫覆盖，再让监听触发一次
只是重复劳动。

**监听的失败是静默的。** `C:\System Volume Information` 这类目录打不开是权限边界，
不是错误；`DirectoryWatcher::watch` 只记一条 debug 日志并退回「未监听」，
该目录因此不会自动刷新，但打开它照旧。把这条失败弹给用户，只会制造一个
「为什么这个文件夹打不开」的假问题。

**隐藏文件为什么在载入时过滤，而不是在 `scan` 里。** 「有没有隐藏属性」是平台事实，
「要不要显示」是用户偏好，两者混在同一个 `scan` 参数里会让平台层去理解配置。
放在批次并入的那一步（`begin_load`）还有一个额外好处：`entries` 与 `visible()`
共用同一份下标空间，选中集、框选、右键菜单都不必再关心隐藏文件是否混在里面。
代价是切换开关要重扫一次（20k 条目约 44ms），这比维护两套下标映射便宜得多。

**IPC 用命名管道，不用 `WM_COPYDATA`。** 后者需要拿到窗口句柄并挂上自己的窗口过程，
而 GPUI 的窗口过程不对外开放；管道是一个完全独立的通道，不碰 UI 框架的任何内部约定。
主实例的监听线程常驻、只在重复启动时被唤醒一次；槽位只保留最后一次请求——
用户连点两次「用叠页打开」，执行第一次就已经满足了他的意图。

## 系统图标：按扩展名取，自己编 PNG

图标是这条渲染链上唯一「不是我们自己生成」的像素，因此有三个绕不开的决定。

**一、按扩展名而不是按路径取。** 按路径（`SHGFI_ICON` 不带 `USEFILEATTRIBUTES`）
能让每个 exe 显示自己的图标，代价是每进一个目录就要为每条 exe 打开文件、读资源段，
而且几乎无法缓存（路径基本不重复）。按扩展名则用 `USEFILEATTRIBUTES` + 一个
**不存在的**假文件名 `pagefold-placeholder.<ext>`，让 shell 只回答「这个扩展名用哪张图」——
这正是资源管理器在缩略图视图下的行为，缓存粒度也天然是扩展名。
代价是「所有 exe 长得一样」，这个代价换个角度是收益：一屏 500 个文件只提取一次。

**二、用 `CreateDIBSection` + `DrawIconEx` 而不是 `GetDIBits`。**
`HICON` 不能直接读像素。`GetIconInfo` + `GetDIBits` 是一条路，但请求 `BI_RGB` 时
32 位图标的 alpha 会被丢掉，只能再补一遍 mask 合成；而 `DrawIconEx(..., DI_NORMAL)`
画到 32bpp DIB 上时，系统已经替我们完成了 alpha + mask 的合成。
代价是要管一个内存 DC，且**必须先把像素拷出来再 `DeleteObject`**——
先释放后读取是一块已释放内存，会直接崩（实现时踩过一次，测试现在覆盖了它）。

**三、自己编 PNG 交给 GPUI。** `img()` 只接受资源路径、`RenderImage` 或
「编码字节 + 格式」。`RenderImage` 需要 `image::Frame`，而 `image` 不是（也不该成为）
本项目的直接依赖；资源路径要求图标落盘，为一个内存位图写临时文件不可接受。
于是剩下「编码字节」这一条：**PNG 的 deflate 只用存储块**（不压缩），
编码器因此不需要任何压缩算法依赖，几十行即可写完，32×32 的产物约 4KB。
编码结果按 `IconId` 缓存，同一个扩展名只编一次。

**句柄与分层。** `Entry::icon: IconId` 本来就是为这件事预留的。分配句柄的一侧
（`fm_services::icon::IconCache`）在扫描线程里调 shell 并把位图登记进
`fm_core::icon` 的进程级注册表；渲染的一侧（`fm_views::icon_image`）用句柄取回、
编码、交给 GPUI。走注册表而不是层层传参，是因为位图不参与布局与状态流转：
给它给三个渲染入口各加一个参数，收益为零。

**兜底。** `IconId(0)` 表示「没有系统图标」，此时退回内置 SVG 图标
（`widgets::entry_icon` 的扩展名分组）。驱动器与符号链接一律走兜底：
前者要真实盘符才拿得到卷图标，后者在资源管理器里表达的是「带箭头的目标」，
都不是扩展名能描述的语义。

## 文件写操作的设计

入口有三处，**共用同一套动作定义**（`crates/shell/src/context_menu.rs` 的 `MenuAction`）：
内容区右键菜单、选中条的动作组、命令条右端的「新建」下拉。同一个动作在应用里只有一处定义，
否则措辞与禁用逻辑迟早分叉。

### 分层

| 层 | 负责 |
| --- | --- |
| `fm-core::naming` | 名称校验（非法字符、保留设备名、长度按 UTF-16 码元计）、扩展名切分、重名去重 |
| `fm-platform` | 真正的 IO：新建、改名、复制、移动、移入回收站 |
| `fm-services::clipboard` | 应用内剪贴板：复制 / 剪切的状态，以及「这次能不能粘贴」的判定 |
| `fm-services::ops` | 编排：提交前校验名称、分派动作、把回执翻译成一句人话 |
| `fm-shell` | 后台线程执行 → 弹提示 → 刷新列表；以及内联重命名与确认对话框 |

### 几个刻意的选择

**冲突策略是「自动改名」，且永不静默覆盖。** 新建与粘贴遇到重名会得到
`新建文件夹 (2)` / `报告 (2).docx`（序号插在主干与扩展名**之间**，与资源管理器一致），
而不是覆盖或报错。反过来，**重命名**是用户明确给出的名字，重名就报错——
你输入 `报告.docx` 却得到 `报告 (2).docx` 是更坏的结果。
注意 `fs::rename` 在 Windows 上走 `MOVEFILE_REPLACE_EXISTING`，默认会**静默覆盖**
同名目标，因此改名路径上有一道必需的存在性检查（见 `crates/platform/src/windows/fs_ops.rs`）。

**复制与移动走 `std::fs`，只有删除走 shell。** `SHFileOperation` 能免费拿到系统进度条，
但它只回一个错误码，说不出「已复制 3 项，1 项因占用失败」，而 UI 需要的是逐条回执
（`OpReport`）。真正非 shell 不可的只有「移入回收站」——那不是文件系统操作，
而是 shell 的语义：要在每个卷的 `$Recycle.Bin\<SID>\` 下写一对 `$I`/`$R`。

**长路径。** Rust 的 `std::fs` 不会给路径加 `\\?\` 前缀，因此超过 260 字符会直接失败。
对文件管理器来说这不是边角情况（`node_modules` 里三层就两百多字符），所以平台层的
每一次 IO 都经过统一的转换——含 UNC 改写成 `\\?\UNC\`，以及路径里出现 `.` / `..`
时的保守回退（加前缀后系统不再做规范化，`..` 会被当成一个字面量的目录名）。

**跨卷移动**自动退化为「复制 + 删源」：`rename` 无法跨卷，而用户不该关心两个盘
是不是同一个卷。

**移入回收站用独立线程。** `SHFileOperationW` 在需要显示进度时要有能泵消息的线程，
借 GPUI 的后台线程去跑等于让它的消息泵去服务另一套 UI；因此每次删除起一个短命线程。
标志位是 `FOF_ALLOWUNDO`（核心，没有它就成了永久删除）+ `FOF_NOCONFIRMATION`
（确认框我们自己出）+ `FOF_WANTNUKEWARNING`（超过回收站配额、将被永久删除时**仍然要问**）。
刻意不加 `FOF_SILENT`：宁可让系统显示自己的进度条，也不要让删一个几 GB 的目录
看起来像卡死。返回值为 0 也要再查一次 `fAnyOperationsAborted`——用户可能在系统进度条上
点了取消，那时报「已删除 3 项」就是在说谎。

**新建之后立刻改名，为此不走「等扫描完成」那条路。** 设计稿的 `makeFolder()` 是
「建完立刻进入重命名」，而目录扫描是异步的（大目录要几百毫秒）。因此新建成功后
直接把那一条**插进列表**——元信息用紧接着的一次 `stat` 取真（不是拼出来的近似值），
插完按当前排序键重排、选中它，然后立刻拉起输入框。代价是：新建时若正好有一次扫描在途，
那次扫描会被作废（否则它剩下的批次回来时会与手动插入的这一条重复），列表因此可能
停在半截。这个「欠一次刷新」记在 `ShellView::list_incomplete` 上，
等重命名会话结束（不管有没有真改名）补上。

**可预见的失败都在提交前拦住。** 「名称不能包含字符『?』」「该名称是 Windows 保留的设备名」
这类判断在 `fm-core::naming` 里做完，而不是等系统回一个 `Os { code: 123, .. }`。
平台层只负责一件需要看文件系统才能决定的事：重名怎么办。

### 三处与设计稿的差异

1. **新建之后一律进入重命名**，文件夹与文件都是。设计稿只对文件夹这么做
   （`makeFolder` 进改名，`makeFile` 只弹一条提示）。统一成一种行为是为了不让人去猜
   「为什么建文件夹能直接改名、建文件却不能」，而且带序号的默认名
   （`新建文本文档 (2).txt`）反而更需要马上改——资源管理器也是直接进改名的。
2. **`Esc` 的行为**：组件库的输入框开启 `clean_on_escape()` 后会**清空内容**
   （本项目的搜索框用的是同一套），随后失焦即按放弃处理（空名不会被提交）。
   设计稿的「Esc 直接收起输入框」需要一个全局 `Esc` 动作，而它和输入框自身的
   Esc 处理、弹出菜单的 Esc 关闭处在同一条按键链上，需要先定一套优先级约定；
   键位集中在 `crates/shell/src/actions.rs`，该约定落地后在这里补一个动作即可。
3. **危险色的落点**：确认框的确定按钮用 `ButtonVariant::Danger`，而不是像设计稿那样
   把菜单项本身染红——组件库的菜单项渲染没有危险态变体，为此改成自绘会连带丢掉
   图标列对齐、勾选态与禁用态等现成能力。

### 组件库的一处坑：浮层必须自己挂

`gpui-component` 0.6.4 的 `Root::render` **不渲染通知层与对话框层**——它只渲染
「你的那个视图 + 文字选择层 + 几个 overlay」。这两层必须由**应用自己的视图**挂上：

```rust
.children(gpui_component::Root::render_notification_layer(window, cx))
.children(gpui_component::Root::render_dialog_layer(window, cx))
```

少了这一步的后果很有欺骗性：`push_notification` 与 `open_alert_dialog` 都**静默失效**
——提示和对话框都不出现，也不报错，调用点看起来完全正常。这条约定的出处是库自己的测试
（`dialog/dialog.rs` 里的 `DialogHost` 就是手动调用 `Root::render_dialog_layer(...)` 的）。

本项目的这两层挂在 `ShellView::render` 最外层 div 的末尾（放在最后 = 画在最上层；
两层自身都是 `absolute().inset_0()`，不参与 flex 布局，因此不影响任何区块的尺寸）。
顺带把通知的落点从组件库默认的右上角改成了设计稿的左下角（`left:14px; bottom:40px`）。


## 传输进度与取消：三个刻意的限制

### 一、取消发生在文件边界

`fs::copy` 是单个阻塞调用，没有「写到一半停下」的干净办法。若强行在复制中途返回，
留下的是一个**半截文件**——用户看到它存在、大小不对，却没有任何标记说明它是坏的。
因此取消的语义是：当前这个文件会写完，之后不再开始下一个。
资源管理器的行为与此一致，这里只是把它写进契约。

代价是「取消一个 5GB 单文件」要等它写完。这个代价换的是「不会产生损坏的文件」，
在这两者之间没有第三个选项。

### 二、不画百分比进度条

复制开始前我们并不知道一棵目录里有多少文件；要知道就得先完整遍历一遍——
那是第二次 IO，对机械盘意味着进度卡出现前的长时间无响应。
按「顶层条目数」推进的百分比会在「只复制一个 5GB 目录」时几乎不动，比不画更让人焦虑。

因此进度卡只给**确定的信息**：已处理多少个文件、当前正在处理哪一个。
用户能据此判断「它在动」以及「大概还要多久」，而不需要一条会骗人的条。

### 三、阻塞 IO 走独立线程，UI 轮询取进度

- 复制/移动在 `pagefold-transfer` 线程里跑（不是后台执行器：`fs::copy` 会占住工作线程）；
- 进度写进 `Arc<Mutex<Transfer>>`，UI 侧每 120ms 读一次并 `notify`，直到后台置 `finished`；
- 收尾统一在 UI 线程做（结算剪贴板、记撤销、弹回执、刷新列表）。

取消只是往同一个结构里置一个 `CancelToken`（`Arc<AtomicBool>`）：单向、幂等、随时可读，
不需要在复制递归的每一层处理消息。

**取消之后**：不结算剪贴板（剩下的条目用户很可能想再粘一次），
但已经复制成功的部分仍然入撤销栈——那是真实发生的磁盘变化。

## 递归搜索：独立的一条管线

普通列目录是「一层、几十到几千条」，递归搜索是「一棵树、可能几十万条」。
两者共用一条扫描通道，会让「打开目录」也被搜索的体量拖慢。因此搜索自成一条：

```text
输入框（每次改动）→ 取消上一次 → 后台线程深度优先遍历
                  → 每 64 条回传一批 → ambient_tick 取走追加
                  → 收工时排序一次 → 「N 项」
```

### 四条边界

1. **上限 2000 条**。用户要的是「找到那个文件」，不是「导出整个磁盘」；
   超过之后继续扫只是在烧 IO。
2. **不进入符号链接 / 目录联接**，与复制那边同理：一次误入指向上级的联接就是死循环。
3. **跳过 `$Recycle.Bin` 与 `System Volume Information`**：读不到，内容也没有搜索价值。
   其余没权限的目录一律跳过——一次搜索不该变成一串「拒绝访问」弹窗。
4. **每敲一个字重来一遍**。目录树遍历没有低成本的增量更新，而取消是立刻生效的
   （每处理一条查一次标志）。代价只是「重新走一遍已经走过的目录」。

### 结果列表就是「当前列表」

`visible()` 在有搜索结果时返回它，否则返回当前目录的条目。下游（渲染、选中、
右键、双击、拖出）只认 `Entry`，因此不必为「搜索结果」再造一套交互——
搜到的条目可以直接打开、复制、拖出去。

导航或刷新会**清掉**搜索结果：它属于「另一个目录树」，留着只会让人以为
新目录里列着旧目录的东西。

### 排序放在收工时

边搜边排会让结果在用户眼前反复跳动（每来一批都要重排）。
只在 `done` 那一次排序，过程中保持「发现顺序」——那也是最符合直觉的顺序。

## 三处界面细节：禁用项可读、视图模式沿袭、提示统一在底部

### 一、菜单项悬停 / 禁用看不清：`theme.tokens` 是快照

真正的成因不是「颜色调浅了」，而是**组件库有两套颜色，我们只同步了一套**：

- `apply_component_theme` 改的是 `theme.accent` / `theme.accent_foreground` 这些字段；
- 而菜单项与列表行的悬停、选中读的是 `theme.tokens.accent` / `tokens.accent_foreground`；
- **`theme.tokens` 是主题构造时按库自带配色算出的快照**，改 `theme.*` 不会同步过去。

**更难缠的一点：这一对颜色还来自两个不同的地方。**

```rust
// 组件库 menu_item.rs 的悬停/选中样式
this.bg(cx.theme().tokens.accent)          // 底色：tokens 快照
    .text_color(cx.theme().accent_foreground)  // 文字：theme 字段
```

而我们给 `theme.accent_foreground` 的映射是 `tokens.surface`——浅色下近白、
深色下近黑。于是「浅灰底 + 白字」「深灰底 + 黑字」，鼠标一移上去文字就消失。
只改 `tokens.accent_foreground` 完全无效，因为那一处根本没读它。

现在两半都写成我们的取值：

```rust
theme.tokens.accent = tokens.hover.into();   // 悬停底色：半透明覆盖层
theme.accent_foreground = tokens.fg;         // 悬停文字：正常前景色
theme.tokens.accent_foreground = tokens.fg.into();  // 给补全菜单等兜底
```

注意文字**不能**用 `surface`，那正是这个 bug 的形状。`menu_hover_palette` 把它抽成
纯函数，并有一条回归测试盯着「文字必须是 `fg`、且不等于 `surface`」。

`apply_component_theme` 末尾还有一条 debug 日志，把**组件库真正会读的**两个值打出来
（`tokens.accent.background` 与 `theme.accent_foreground`）——排查这类问题时要看它，
而不是看我们以为它读的那个字段。

至于禁用项，组件库的 disabled 样式是「`muted` 底 + `muted_foreground` 字」，而我们把
这两个字段分别映射成了 `hover` 与 `muted_fg`——两个相邻的灰，叠起来同样读不清。
因此禁用项改用 `PopupMenuItem::element` 自绘（文字取 `tokens.muted_fg`，底就是正常菜单底），
并**保留可点**：点了弹一句「『粘贴』当前不可用」，比一个完全没反应的行更有用。

另有一条配色守卫：`tokens` 的测试用 WCAG 公式算「悬停底色 × 前景色」与
「面板底 × 次级文字」的对比度，深浅两套都要求 ≥ 4.5:1。半透明色先合成到面板底上再算——
直接拿它的 RGB 会得出「对比度 1:1」这种假结果。

### 二、新标签要沿袭视图模式

`TabState::new` 的默认视图是图标视图。用户切到详细信息视图后每开一个新标签都会被
打回图标视图，观感就是「这个设置记不住」。

视图模式属于「用户的工作方式」而不是「某个目录的属性」，所以新标签应当沿袭**当前标签**
的模式（不是 `config.view_mode`——那个是重启后的默认值，此刻未必一致）。
规则放在 `TabsState::open_at_like_active` 里而不是外壳：它只依赖标签自己的状态，
不碰窗口，因此可以直接单测。

### 三、操作反馈只有一个位置：底部居中

原先通知在左下、传输进度卡在右下，两个「刚才发生了什么」的反馈分处两个角，
用户得来回扫。现在统一到**底部居中**这一条带：

- 通知靠 `Theme.notification.placement = BottomCenter`（写在 `apply_component_theme` 里——
  主题切换会重建 theme，只在 bootstrap 设一次会被打回右上角）；
- 进度卡用「左右都贴 0 + `mx_auto`」把定宽卡片推回中线。

两者同时出现时通知会盖住卡片顶部一小块：传输途中弹提示是少数情况，
而把通知整体抬高会在「没有传输」时显得悬空，权衡后选了前者。

## 传输进度：为什么要分块复制，以及为什么有时没有百分比

### 分块才有字节进度

`fs::copy` 是一个整块调用：中间没有任何回调点，因此「复制一个 5GB 的文件」期间
界面只能显示「已处理 1 个文件」——看上去像卡住了。改成 1MB 一块的循环后，
每块结束回报一次 `bytes_done`，进度条才真正会动。

**代价一：修改时间要自己补。** `fs::copy` 会带上源文件的修改时间，自己写就必须显式
`SetFileTime`——否则复制出来的文件「修改时间」全是现在，按日期排序时整批跑到最前面。

**代价二：取消会留下半截文件。** 块级取消发生时那个文件已经不完整，因此取消路径
必须 `remove_file` 把目标删掉。宁可少复制一个，也不能留一个看起来正常、实际截断的文件。

### 为什么有时不显示百分比

`bytes_total` 只在「源全是文件」时才能廉价算出。源里一旦有目录，总大小要先遍历整棵树，
而多遍历一遍就是第二次 IO——对一个几十万文件的目录，用户会为了一次进度条多等好几秒。

因此：`bytes_total == 0` 表示**未知**，界面只显示「已复制 12.3 MB」，不画进度条。
给一个随发现不断跳动的假百分比，比不给更糟。

## `\\主机` 不是目录：网络共享要走 NetShareEnum

`\\主机\共享` 是普通目录，`read_dir` 就能读。但 `\\主机` 本身在 Windows 里**不是目录**
（`Path::is_dir` 恒为 false，`GetDirectories` 直接报「UNC 路径的形式应为 \\server\share」）。

这正是一句「路径不存在」的来源：地址栏拿 `is_dir` 做校验，于是把一台待列举的主机判成了
不存在的路径。修法是两条：

1. 平台层把「只有服务器名」的路径识别出来，走 `NetShareEnum` 列磁盘共享
   （资源管理器打开 `\\主机` 用的是同一套网络 API）；
2. 地址栏与导航接受这种路径，并且**错误文案要分开**——网络失败的原因通常是
   「主机不可达 / 共享不存在 / 需要凭据」，说成「路径不存在」会让人去查名字。

需要凭据的共享用 `WNetAddConnection2W(CONNECT_INTERACTIVE)` 让系统弹凭据框并重试一次，
这也正是资源管理器的行为。管理共享（`C$` / `ADMIN$`，带 `STYPE_SPECIAL`）标记为隐藏。

### 共享打印机会被「只看磁盘」漏掉

`NetShareEnum` 返回的每一条都带 `shi1_type`，用户在资源管理器里看到的「共享打印机」是
`STYPE_PRINTQ`，而最初只判了 `STYPE_DISKTREE`，于是「有打印机却一台都看不到」。

两处容易判错，都写进了单测：

1. **`STYPE_DISKTREE` 的值就是 0**，所以不能拿它当「非零才算合法」的哨兵；
2. 真实共享几乎总带着附加位（管理共享的 `STYPE_SPECIAL`），判定必须**先与 `STYPE_MASK` 取与**。

打印机在列表里用独立的 `EntryKind::Printer` 表示，而不是塞一个魔法扩展名：它决定了
图标（打印机）、类型列文案（共享打印机）、双击行为（交给 `ShellExecute` 打开打印队列），
以及「复制 / 重命名 / 删除」这些写操作要不要在入口就拦下（拦下时说明原因，
而不是让系统调用来抛一条用户读不懂的错误码）。`IPC$` 之类的命名管道不列——
它们既不能浏览也不能打开。

## 改键即重建键位表：`clear_key_bindings()` 会连库的一起清掉

自定义快捷键要在改完之后**立刻生效**，而 `cx.bind_keys` 是累加的：只叠加会让旧键位
继续有效（「改了这个键，结果两个键都能用」）。所以每次应用都先
`cx.clear_key_bindings()` 再整体绑定。

这一行有个大坑：`clear` 清的是**整张表**，包括 `gpui_component::init` 里注册的
那些——输入框的 `backspace` / `enter` / `ctrl-a` / 方向键 / Home/End 全在里面。
清掉之后不补回去，后果很有欺骗性：

```text
能打字（走平台的文本输入通道，不经过键位表）
但删不掉（backspace 依赖键位表里的 Backspace 动作）
→ 用户会说「退格键在输入框里不生效」，而它其实从来没有“被拦截”
```

修法是「抄—清—补」：`ShellView` 在**第一次**应用之前把库自带的绑定抄一份
（`shortcuts::snapshot`），之后每次重建都是：清空 → 补回库绑定 → 绑定我们的。

```rust
cx.clear_key_bindings();
cx.bind_keys(base.to_vec());   // 库自带，必须先回来
cx.bind_keys(bindings(config)); // 我们的
```

快照必须在**我们还没绑过任何东西**时取，抄到的才是纯库绑定；
放在 `ShellView::new` 里（此时 `gpui_component::init` 已跑过）正好满足。

### 另一个入口问题：光标位置

`InputState::default_value(路径)` 会把光标停在 **0**，于是

- 打字是在开头插入（「从头开始编辑」）；
- 光标在 0 时退格没有东西可删（「退格不生效」）；
- 也不像资源管理器那样「点进去整条路径全选」。

改法是 `set_value(..)`（单行输入会把光标放到**末尾**）再 `select_all(..)`。

### 怎么判断「卡在键位表」还是「被谁拦截了」

按键分发的大致顺序（`gpui` 的 `dispatch_key_event`）：

1. 按**上下文深度**排序所有匹配绑定，深的先试；同深度后注册者胜；
2. 依次把 action 派发给焦点路径上的监听器，**只有真的被处理才停止**；
3. 都没处理才走到 `on_key_down` 监听器。

所以「某个键在输入框里没反应」通常是第 1 步里**它的绑定没进表**（被清掉了），
而不是被别的处理器抢走。想确认，就在输入框的 `InputEvent::Change` 上打日志，
再用 `PostMessage(WM_KEYDOWN)` 注入按键——不需要前台窗口，比 `SendInput` 好使。

## 设置页的滚动性能：先量，再改

「加了快捷键设置之后，这页滚起来很卡」——先测再动手，量了三件事：

| 指标 | 结果 | 结论 |
| --- | --- | --- |
| 单帧里**构建元素**的耗时 | 0.3–0.9 ms（release）/ 1–3 ms（debug） | 不是瓶颈 |
| 滚轮时的**帧间隔**（设置页，25 行） | 27–47 ms | 约 25 fps |
| 滚轮时的**帧间隔**（文件列表，同一份程序） | 18–45 ms | **同样是 ~30 fps** |

最后一行是关键对照：这台机器（远程/虚拟环境，无 GPU 加速）上**整个应用**就在 30 fps 左右，
不是设置页独有的问题。但行数确实会加重：同样条件下 3 行 → 约 95 ms、25 行 → 约 140 ms（debug 下），
说明**每一行都参与布局**，即使它在屏幕外。

据此做了三件事，按收益排序：

1. **分组折叠**（默认全折叠）。25 行铺开时页面接近两屏，而折叠后只渲染 6 个组标题，
   用户点开自己关心的那一组。这是唯一能把「行数」这个变量真正压下去的办法——
   布局是按整棵树算的，靠「只画可见区」优化在 GPUI 这层做不到。
2. **去掉行内的 tooltip**。行尾「修改」原来是 `widgets::text_button`，它自带 tooltip；
   25 行 = 25 个 tooltip，滚轮划过时不断创建/销毁提示实体。换成轻量链接（只有 hover 变色）。
3. **清单与冲突改缓存**。设置页每帧重建整棵树，`resolve()` 25 条命令 + 建 BTreeMap 每帧重算一遍
   纯属浪费；改成配置变化时才刷新。

顺带一个结论，供以后判断「卡」时参考：**先看 `build_ms` 与 `since_last_ms` 的差值**。
差值大，说明慢在布局/绘制（元素数量、文字量）；差值小，才是慢在我们自己的代码里。
这次两个探针都留下来当方法论，代码里的临时插桩已移除。

## 全局热键：为什么最终不用键盘钩子

早期版本用 `WH_KEYBOARD_LL` 抢 `Win+E`。那条路走不通，而且**每一步都是实测出来的**：

| 尝试 | 现象 | 结论 |
| --- | --- | --- |
| 吞 `E`，其余放行 | `Win+E` 能用，但开始菜单跟着弹（Win11 先铺一层暗色遮罩，看起来是屏幕暗一下又亮） | 有副作用 |
| 吞 `E` + 吞 `Win` 抬起 | 开始菜单没了，但系统收不到释放 → 之后所有按键都变成 `Win+字母`（打字失灵） | 更糟 |
| 吞 `E` + 补发 `F24` | 无效：开始菜单照弹 | 假事件不被承认 |
| 补发合成的 `Win` 抬起 | 无效：`SendInput` 一个 `LWIN` 按下，`GetAsyncKeyState` 依然是抬起 | Windows 丢弃合成 Win 事件 |

最后一条是关键证据：**合成的 Win 键事件根本进不了输入流的组合判定**，
所以「用假事件修补」这条路从根上封死；而「吞真实抬起」又会污染键状态。

于是换成 `RegisterHotKey`：由系统分发这个组合，既不吞键也不会被当成「单独按了 Win」。
代价明确——**只能注册没被占用的组合**，`Win+字母` 全被 shell 占着，
因此默认值取 `Ctrl+Alt+E`，并在设置页把 `Win` 组合标成「系统占用，无法注册」。

### 配置怎么传到宿主

宿主是独立进程（主窗口关了热键仍要有效），但它不依赖 `fm-services`：

```text
主程序：写 %APPDATA%\pagefold\hotkey.txt ──▶ PostMessage(hwnd, WM_HOST_RELOAD)
宿主：读文件 → 注销旧注册 → 注册新组合
```

用文件而不是把字符串塞进消息：`PostMessage` 只带两个整数，传递字符串要么再引入一套
序列化，要么跨进程分配内存。文件在这里是最简单的「共享状态」。

### 启动顺序有个坑

`hotkey.txt` 必须在**拉起宿主之前**写好，否则宿主读到的是上一次（或空的）配置，
表现为「改了热键要重启两次才生效」。因此 `main` 里先 `sync_global_hotkey_spec()`
再 `spawn_hotkey_host()`。

### 冲突检测分两层

- **纯规则层**（`fm_core::shortcut::conflicts`）：内部命令之间、命令与全局热键之间，
  按规范化后的组合比较（`Ctrl+C` 与 `ctrl-c` 是同一个），并且只统计**启用**的那些
  ——把一条禁用掉本身就是解冲突的手段，界面上要这样提示；
- **系统层**（`fm_platform::probe_hotkey`）：真的 `RegisterHotKey` 一次再注销，
  用来发现「被别的程序占着」。**只在用户改成新组合时调用**——
  设置页每帧都会重建快照，每帧探测一次既不必要，而且宿主本身正占着当前组合，
  探测必然失败，会误报成「被占用」。

### 改键立刻生效

`cx.bind_keys` 是**累加**的，所以每次改键都 `clear_key_bindings()` 再整体绑定。
不这么做的话，旧键位仍然生效，表现为「改了这个键，结果两个键都能用」。

### 录制浮层为什么自己做

按键事件只沿**焦点路径**分发，系统对话框拿不到 GPUI 的按键事件。因此点「修改」后
弹一个整窗遮罩，把焦点交给它，`on_key_down` 里把 `Keystroke` 交给
`fm_core::KeyCombo::parse` 归一化（别名、白名单、大小写都在那一处，避免两套规则）。
只按修饰键时不算错误——那是「还没按完」。

## 预览正文的可复制性：用只读输入框，不要自己实现选区

预览面板要能「选中文字并复制」。GPUI 的普通文本**没有选区**，自己实现意味着
要做文本换行布局、命中测试、高亮分块绘制——一套小型编辑器。

因此正文交给组件库的多行输入框，并设为只读：

```rust
Textarea::new(&state).readonly(true).appearance(false).bordered(false).h(px(220.0))
```

`readonly` 与 `disabled` 的区别正是这件事的关键：**readonly 保留聚焦、框选与复制，
只拒绝改动**（组件库文档写明的）。`disabled` 会把这三项一起拿走，那是错的。

### 代价：它会夺走焦点

这也正是想要的行为：焦点在正文里时，`Ctrl+C` 复制的是**选中的文字**，
`Ctrl+A` 选的是**文本**，而不是文件。列表快捷键挂在内容区上
（见「键盘」那节），此时不在分发路径里，所以不会误伤文件。点回列表即恢复。

### 三条实现约束

1. **实体由外壳持有**，视图每帧只借用。渲染函数里 `cx.new` 会让每帧都产生一个
   全新的输入框（与内联重命名同一个坑）。
2. **同步放在 `render` 里**：输入框的 `set_value` 需要 `&mut Window`，
   而 `ambient_tick` 只有 `Context`。`render` 是唯一既有 `window` 又能感知
   内容变化的地方；放在渲染之前，面板这一帧就是最新内容。
3. **`set_value` 只在内容变化时调用**：它会重置选区，每帧无条件写一次
   会把用户刚框选的文字清空。
4. **高度固定 220px**，不按行数撑开：面板只有 306px 宽，长行会折行，
   「行数 × 行高」算出来的高度必然偏小、把末尾切掉。

## 标签条溢出：先压缩，再横滚

标签的宽度区间是 96–176px。多得装不下时有两种做法：

| 做法 | 后果 |
| --- | --- |
| 继续压缩 | 标题只剩一两个字，一排标签看不出分别是哪个目录 |
| 到下限就横向滚动 | 每个标签仍然可读，代价是需要滚动 |

选后者。实现上有三个要点：

1. **压缩与滚动的分工交给 flex**：`flex_shrink(1.0)` + `min_w(96px)` 让标签先均匀压缩，
   压到下限后自然溢出，`overflow_x_scroll` 接管滚动。不需要手动算「能放几个」。
2. **滚轮要翻译成横滚**：标签条只有横向可滚，竖向滚轮在这里没有别的含义。
   不接管它，鼠标用户就只能靠触控板。偏移量夹在 `[max_offset, 0]` 之间——
   偏移是负值，不加夹取会把标签条滚到一片空白上。
3. **当前标签必须自动进视野**：新建、`Ctrl+Shift+T` 恢复、键盘/菜单切换都可能把
   目标标签留在视野外。`ScrollHandle::scroll_to_item(下标)` 在切换点调用一次即可
   （每帧都调会与用户的手动滚动打架）。

## 预览面板：按内容判断「能不能预览」

面板右侧在选中单个文件时显示**内容**：文本给开头，图片给大图，其余只给元信息。

### 一、判断文本看内容，不看扩展名

扩展名只能覆盖常见类型，而最想瞄一眼的往往是 `README`、`LICENSE`、`.gitignore`
这类没有扩展名的文件。因此规则换成：**前 8KB 里出现 NUL 就是二进制**——
与 git 的做法一致，简单，且几乎不会误判（文本文件里不该有 NUL）。

只嗅前 8KB 还有一个好处：截断处那半个 UTF-8 字符不会被误判成「二进制」，
`from_utf8_lossy` 会把它换成替换字符。

### 二、上限是产品决定，不是防御性编程

- **32KB**：面板 306px 宽，12px 等宽字号下一屏二十来行；32KB 已经够翻很久。
  读整个文件则可能碰上 4GB 的日志，直接卡死后台线程。
- **200 行**：超出以「…」收尾。面板可以滚动，但「滚不到底的滚动条」
  比「明确告诉你截断了」更让人困惑。

### 三、异步，且绝不显示上一条的内容

读取在后台任务里做（选中后约 400ms 出现）。三个状态要分清楚：

| 状态 | 含义 | 面板表现 |
| --- | --- | --- |
| `preview_text` 里没有这个路径 | 还没读 | 只显示元信息 |
| `Some((path, None))` | 读过，不是文本 | 只显示元信息（**不要每帧重读**） |
| `Some((path, Some(text)))` | 读到了 | 显示正文 |

回写时还要再核一次路径：用户可能已经切走了，而读取刚好在这之后返回——
不核对就会把上一条文件的内容显示在新选中的条目下面。

### 四、图片复用缩略图，不另起一条路

图片的「大图」就是缩略图放大到 112px：同一个句柄，同一份缓存。
面板头图原本是 44px 的小图标，放在 132px 的底板里像「没取到缩略图」，
所以有缩略图时改成铺满。

## 缩略图：异步、白名单、别要「更大的图」

图标视图里，图片 / 视频 / PDF 显示的是**真实缩略图**，其余文件仍是扩展名图标。

### 一、取图必须离开渲染路径

真实解码一张照片要几十毫秒，视频还要抽帧。目录里几百张图时，在渲染路径上现取
等于把界面冻住。因此请求与渲染彻底解耦：

```text
渲染：先画扩展名图标（立刻可见）
ambient_tick（400ms）：收货 → 把条目 icon 换成缩略图句柄 → 重绘
工作线程：单线程依次解码（视觉上从上往下逐格出现，而不是随机闪）
```

单线程是刻意的：缩略图属于背景美化，不该和用户的实际操作抢 CPU 与磁盘。

### 二、只对白名单发请求

`IShellItemImageFactory` 对**没有**预览处理器的文件会退回它的图标——不报错、也不是空图。
于是「对所有文件都请求缩略图」就变成「用一张高分辨率图标替换我们已按扩展名去重过的图标」：
既浪费解码与内存，观感还更差。因此服务层维护一个白名单（图片、视频、PDF、SVG），
其余类型一律不请求（`is_previewable`）。

### 三、不要 `SIIGBF_BIGGERSIZEOK`

那个标志允许 shell 返回比请求更大的图（命中缓存时常常 256px，某些处理器甚至给原图）。
一张 4000×3000 的照片按 RGBA 展开就是 48MB，一个大目录足以把内存吃光，
而我们最多只画到 192px。去掉它之后，152 的请求得到 152×95（等比、不失真）。

### 四、两个只有真机才会暴露的坑

**相对路径会静默失败。** shell 的解析函数要求绝对路径；从命令行用相对目录启动时，
扫描出来的条目路径是相对的，`SHCreateItemFromParsingName` 直接失败 ——
表现为「缩略图一个都不出现」，日志里也什么都没有。因此取图前统一
`std::path::absolute`。

**刷新会抹掉已取到的缩略图。** `F5` 或自动刷新会重新扫描，`entries` 是全新的
`Entry`（`icon` 回到扩展名图标）。因此 `pump_thumbnails` 每轮都幂等地把
`thumb_ids` 里已有的句柄写回去，而不是「只在收到新结果时写一次」——
在每条刷新路径上各补一次，迟早会漏掉一条。

### 五、等比缩放

`glyph` 渲染位图时用 `ObjectFit::Contain`：照片是 4:3、截图是 16:9，
默认的 `Fill` 会把它们拉变形，而方形图标用 `Contain` 与 `Fill` 的观感完全一致。

## 回收站还原：为什么「移入」要 shell，而「还原」不必

「移入回收站」必须交给 shell：配额、`$I` 版本差异、跨卷时换卷，都是 shell 的语义。
但「还原」不是——**`$R` 内容与其原始位置永远在同一个卷上**，这正是回收站的设计前提。
于是还原只需三步：

```text
$R<id>  →  读同名 $I<id>  →  解析出原路径  →  MoveFile 回原位  →  删掉 $I<id>
```

一次 `MoveFile` 就够了：不必复制、不会跨卷、也不需要进度条。

### 三条必须守住的边界

**1. 原名被占用时自动改名，而不是覆盖。** 用户很可能在原位置又建了一个同名文件；
覆盖会毁掉那个新文件，而直接报错又让他无从下手（他还得自己先去改名）。
沿用与复制粘贴相同的 `unique_name`，结果是 `报告 (2).txt`。

**2. 元数据损坏时拒绝搬运。** `$I` 读不出来就无法确定原位置。
此时**宁可报错也不能猜**——猜错会把内容搬到一个用户完全想不到的地方，
比「还原失败」严重得多。删除中途断电留下的 `$I` 截断、`$R` 缺失的条目，
在枚举阶段本来就会被跳过，还原这里再兜一次。

**3. `$I` 删不掉不算失败。** 内容已经回到原位，此时报错只会让用户以为没还原。
删不掉的 `$I` 会在下次枚举时因为找不到 `$R` 而被自然忽略。

### 撤销「移到回收站」：8.3 短名会让路径比较失败

撤销时手里只有**原路径**（移入时 shell 不告诉我们 `$R` 叫什么），只能枚举回收站反查。
第一版直接比较字符串，测试里立刻失败：

```text
$I 里记的：C:\Users\Administrator\AppData\Local\Temp\...
我们手里的：C:\Users\ADMINI~1\AppData\Local\Temp\...      ← %TEMP% 就长这样
```

同一个文件，两种写法。因此比较前要把两边都规范成「长名 + 小写」：
对被删文件**只展开它的父目录**——文件本身已经不存在，`GetLongPathNameW` 会失败，
而父目录还在，足以把短名展开。

### 清空：仍然交给 shell

`SHEmptyRecycleBinW` 带三个标志：`NOCONFIRMATION`（确认框由我们自己出，
用 danger 样式的按钮）、`NOPROGRESSUI` 与 `NOSOUND`（清空通常很快，
弹进度框再「叮」一声反而像出了什么事）。入口只在回收站视图里出现——
普通目录里的一键清空是灾难。

## 双击打开：`ShellExecuteW` 的三个细节

双击的语义是「打开这一项」，与类型无关：目录进入、文件交给系统。**只有目录走导航**，
把目录也交给 shell 会新开一个资源管理器窗口——用户点了「打开」却看到两个窗口。

### 一、不要给 `ShellExecuteW` 加 `\\?\` 前缀

本项目所有文件 IO 都经 `extended()` 加长路径前缀，打开文件这里必须**例外**：
带前缀的路径不会被当成普通文件，扩展名关联查找随即失效，表现为「什么都没发生」。
代价是超过 260 字符的路径打不开——那类路径本来也没有几个程序能正确处理。

### 二、返回值是伪句柄，`> 32` 才算成功

`ShellExecuteW` 返回的不是错误码本身，而是「小于等于 32 时才是错误码」的约定。
因此判定写成 `code > 32`，并把 `0/2/3/5/31` 翻成人话：
「找不到该文件」「没有与该类型关联的程序」这类句子，用户才知道下一步该干什么。

### 三、在后台线程打开

`ShellExecuteW` 会等目标程序的 DDE/COM 握手，冷启动重型程序时可能卡住几百毫秒。
放在 UI 线程上就是「双击后界面僵一下」，因此扔进后台执行器，失败再回 UI 弹提示。

### 回收站条目一律拒绝

回收站里的 `path` 指向 `$Recycle.Bin` 内部（受保护的系统目录），按普通路径打开
要么被拒绝、要么把用户丢进系统目录。正确动作是「还原」，属于尚未实现的回收站写操作，
因此这里明确提示「需要先还原」，而不是静默失败或弹出系统错误。

## 拖入：同一个「不写 OLE」的结论，理由却相反

剪贴板那一节的理由是「我们要**发布**数据，所以得自己写 `CF_HDROP`」；
拖入恰好相反——**消费**数据这件事 GPUI 已经做完了：

```
系统文件拖放 → gpui_windows 的 IDropTarget
             → PlatformInput::FileDrop(Entered { position, paths })
             → cx.active_drag = ExternalPaths
             → 合成 MouseMove / MouseUp
             → 命中元素按「鼠标下方 + 载荷类型」派发 on_drop
```

因此拖入不需要 `OleInitialize`、不需要 `RegisterDragDrop`、也不需要自己实现
`IDropTarget`——内容区只要挂两样东西：

```rust
.can_drop(|payload, _, _| payload.is::<ExternalPaths>())
.on_drop::<ExternalPaths>(cx.listener(|this, paths, window, cx| { … }))
```

### 三个决定

**1. 一律按复制处理。** `FileDropEvent` 只带 `paths`，源程序的
`Preferred DropEffect` 在 GPUI 这一层就丢了。猜「移动」的代价是用户以为文件被
复制、实际却被搬走，甚至源被删——比多留一份副本严重得多。用户想移动，
复制完删掉源即可。

**2. 落在原目录等于空操作。** 把文件拖进它自己所在的目录，资源管理器也不做任何事。
同理，拖进来的路径若已不存在，也直接过滤——静默失败比报错更糟，因此两者都会被
合并成一句「已经在当前目录，或已不存在」。

**3. 松手后复用粘贴那条管线**（`begin_transfer`）：进度卡、取消、逐条回执、
`Ctrl+Z` 撤销全部一致。拖入与粘贴在「把它搬进当前目录」这件事上是同一类操作，
各写一条路径只会让两边的边界行为慢慢分叉。

### 悬停高亮用背景色，不用描边

没有提示的话，用户在松手之前不知道这一下会不会生效。高亮由一个 `drop_active` 标志
驱动：`on_drag_move::<ExternalPaths>` 置位、`on_file_drop_exit` 与 `on_drop` 清除。
样式用**背景色**（强调色 6% 透明度）而不是描边：描边会改变布局宽度，
拖动时内容会横向跳一格。

### 拖出：只在「指针离开窗口」时才变成系统级拖拽

拖出用同一个 GPUI 通道：行/格挂 `on_drag(载荷)` + `external_drag_payload(...)`，
载荷是 `(路径, 是否目录)`。关键在于 GPUI 的
`promote_external_drag_to_platform`：**只有指针移出视口边界**、且平台允许时，
它才会把内部拖拽提升为真正的系统文件拖拽。

这条判定顺手解决了最担心的问题——**框选不会被抢**：

| 操作 | 结果 |
| --- | --- |
| 在窗口内按住条目拖动 | 内部拖拽（预览视图是空的），原有的框选逻辑照旧执行 |
| 拖出窗口边界 | 提升为平台拖拽，资源管理器/桌面按 `CF_HDROP` 接收 |
| 在窗口内松手 | 载荷类型不匹配任何 `can_drop` 目标，什么也不发生 |

**载荷规则**：拖已选中的条目 → 整个选中集；拖未选中的条目 → 只带它自己。
这条规则和资源管理器一致，判断留在外壳层（`drag_out_builder`），
视图层只负责把载荷挂到那一行/那一格上。

**进入编辑态时不挂拖出**：输入框里拖选文字是另一回事，而且那时拖整行会把
正在改名的条目连同旧名字一起拖出去。

## 跨程序剪贴板：为什么不写 `IDataObject`

早期规划写的是「需要 `OleSetClipboard` + `OleFlushClipboard`，`OleInitialize` 必须在主线程」。
那句话对通用数据对象成立，对本程序不成立：剪贴板里永远是**真实存在的本地路径**，
没有虚拟文件、不需要延迟渲染。于是直接写 `CF_HDROP` 就够：

| 格式 | 内容 | 作用 |
| --- | --- | --- |
| `CF_HDROP`（15） | `DROPFILES` + 双 NUL 结尾的 UTF-16 路径 | 文件列表本身 |
| `Preferred DropEffect` | 4 字节 DWORD：1=复制、2=移动 | 告诉接收方该复制还是剪切 |

`SetClipboardData` 成功后内存所有权归系统，**本进程退出后粘贴依然有效**——
这正是 `OleFlushClipboard` 要解决的问题。`Preferred DropEffect` 是可选的：
缺了它，资源管理器按「复制」处理，所以写失败也不影响主功能。

### 三方状态的优先顺序

1. **应用内剪贴板优先**（`services::clipboard` 仍是语义的唯一来源：复制/剪切、
   冲突改名、剪切后失效都在那里）；
2. 应用内为空时，`paste` 回退去读系统剪贴板（资源管理器复制过来的文件）；
   读到的路径先按磁盘现状过滤（剪贴板里可能留着早就删掉的条目），
   「剪切 + 目标就是源目录」的条目直接排除（自己搬自己没有意义）；
3. 两边都没有 → 提示「剪贴板里没有可粘贴的文件」。

### 「粘贴」的可用态为什么是节流的

`OpenClipboard` 与其它程序互斥，每帧探测既慢又容易读到「被占用」的假空。
因此由 `ambient_tick` 节流探测：**只在应用内剪贴板为空时**、约 1.2s 一次，
结果只用于决定菜单项与快捷键提示是否可用；真正的路径在按下粘贴时再读一次。

### 已知限制

- **剪切后不主动清空系统剪贴板**：对方（资源管理器）搬走文件后，我们这边的剪贴板
  仍留着旧路径。再次粘贴时这些路径已被 `exists()` 过滤掉，于是表现为「没有可粘贴的
  文件」而不是错误——比在别的程序手里抢剪贴板安全。
- **不支持 ANSI 列表**（`fWide = 0`）：猜代码页会把中文路径变成乱码，
  粘贴乱码路径的后果比「不支持」严重，因此按「没有文件」处理。
- **`OpenClipboard` 失败即视为空**：用户按 `Ctrl+V` 时收到「剪贴板被占用」毫无帮助。

## 批量重命名：一条纯函数 + 一层浮层

### 命名规则放在 core，且只做「前缀 + 序号」

`core::naming::batch_names(names, spec)` 是**不碰文件系统**的纯函数：输入旧名、
输出新名，序号从 `start` 递增，扩展名按每个条目各自保留（`split_extension` 的规则
与内联重命名完全一致，因此 `archive.tar.gz` 会变成 `前缀1.gz`）。

只有三项参数（前缀 / 起始序号 / 是否保留扩展名）是刻意的：模板语法（正则、占位符）
会把「批量改名」变成一门小语言，而用户真正要做的是「把这些照片改成 旅行_1、旅行_2……」。
需要更复杂的规则时，标准做法是导出列表、用脚本处理、再放回来。

它同时负责三件必须在提交前拦住的事：名称合法性（复用 `validate`）、
批内重名（按小写比较，Windows 不区分大小写）、以及序号溢出——
`start` 接近 `u32::MAX` 时 `saturating_add` 会把多个序号压成同一个数字，
那会生成重复名称，必须报错而不是让第二条 rename 失败。

### 面板是自绘浮层，不是组件库对话框

面板里有两个输入框和一段**实时预览**。组件库的 `Dialog` 内容只在打开时构建一次，
预览不会跟着输入更新；自绘浮层每帧随 `render` 重建，预览天然是实时的。
遮罩用 `.occlude()` 挡住底下的一切，避免误触后面的列表。

## 撤销与永久删除

### 撤销只记「有一条原路可返回」的动作

四种动作可撤销，判据是**逆操作能否用一次系统调用完成**：

| 动作 | 逆操作 |
| --- | --- |
| 重命名 | 改回原名 |
| 新建 | 删掉刚建的东西 |
| 复制粘贴 | 删掉复制出来的那些 |
| 剪切粘贴 | 搬回各自的源目录 |
| 批量重命名 | 整批改回（逆序，互换类改名才不会中途撞名） |

**「移到回收站」不在其中**：它的逆操作是「还原」，需要读 `$I` 元数据、按原路径写回，
那是回收站的写能力（与「清空回收站」一起做）。把它塞进撤销栈的后果是
「撤销了删除但只还原了一半」——比不能撤销糟得多。

两个实现细节：

- **只记成功的条目**。粘贴可能部分失败，失败的那些本来就没动过；
  把它们记进栈，撤销时会去删不存在的路径，报出一串「找不到文件」。
- **新建与随后的改名分成两步**。新建后会自动进入重命名，因此 `Ctrl+Z` 先撤名字、
  再撤创建——这正是连按两次撤销时期待的顺序。
- **撤销不入栈**（没有重做）：把撤销压回栈只会让 `Ctrl+Z` 在两个状态之间横跳。

入口是 `Ctrl+Z` 与空白处菜单的「撤销 <动作>」——菜单里直接写出
「撤销 重命名『报告.docx』」，因为撤销不可预演，用户需要在下手前确认撤的是哪一步。
没有可撤销的东西时整项**隐藏**而不是置灰：置灰意味着「以后会有」。

重命名成功的 toast 里写的是「（Ctrl+Z 撤销）」而不是一个按钮：组件库的
`Notification` 没有动作按钮位，为此自绘一个通知层会连带丢掉队列、超时与主题同步。

### 永久删除必须和回收站删除分开

两者只差一个修饰键（`Delete` / `Shift+Delete`），但可逆性完全不同，因此：

- **两个菜单项**，不是「按住 Shift 改变同一个项的行为」——后者会让用户
  没有地方读到「这一下删了捡不回来」；
- **两套确认文案**：回收站那条说「移到回收站」，永久删除那条明确写「无法撤销」，
  确定按钮都用危险色；
- **逐条回执**：批量删除里一个文件被占用，不该让另外九个白做；
- **只读属性先清掉再重试**：确认框已经问过一次，删除时再失败一次等于让用户在
  两个地方回答同一个问题。清属性只动 `READONLY`，隐藏/系统属性是用户刻意设置的
  标记，与「能不能删」无关。

## 键盘：上下文、焦点，以及一个路由器

这一块踩过一次大坑，四条症状（`Ctrl+Z` 无反应、`F2` 无反应、地址栏退格失效、
回车打不开文件夹）其实是同一个根因的两个侧面。

### 一、快捷键必须带上下文

`gpui-pre 0.3.5` 的 `binding_enabled` 是这么算深度的：

```rust
if let Some(predicate) = &binding.context_predicate {
    predicate.depth_of(contexts)   // 命中上下文 → 该上下文在栈里的位置
} else {
    Some(contexts.len())           // 无上下文 → 栈的**总长度**，即最深
}
```

排序是「深度降序」，同深度再按**注册顺序倒序**（后注册者优先）。
也就是说：**一条无上下文的绑定，优先级等于最深的上下文，且同深度时压过组件库先注册的那条。**

后果：我们的 `backspace`（返回上级）、`enter`（打开）、`ctrl-a/c/v/z`、`up/down`
全部抢在输入框自己的绑定前面。输入框里按退格变成了「返回上级」（被编辑态守卫拦下 → 什么也没发生），
`Ctrl+V` 变成了文件粘贴，`Enter` 变成了「打开选中项」。

### 二、隔离靠「处理器挂在哪」，不靠优先级

只把绑定改成带上下文是不够的——这个版本的排序规则里，**同深度时后注册者胜**，
而应用的绑定总是在组件库之后注册，实测 `Backspace` 依然会被我们的「返回上级」抢走。

真正可靠的做法是利用分发机制的另一半：**按键命中绑定之后，还要沿「焦点节点 → 根」
找到愿意处理它的监听器；找不到就继续尝试下一条绑定。**

于是把两类键分开挂：

| 键 | 挂在哪 | 为什么 |
| --- | --- | --- |
| `Ctrl+T/W`、`Ctrl+L`、`Ctrl+1/2/3`、`Ctrl+,`、`F5`、`Ctrl+3` | 窗口根 | 输入框不用它们，不会冲突 |
| `Backspace`（回上级）、`Enter`（打开）、`Ctrl+A/C/X/V/Z`、`↑/↓`、`F2`、`Delete`、`Shift+Delete` | **内容区**（`wrap_list_area`） | 与输入框自己的按键重合；输入框在命令条里，分发路径不经过内容区，绑定即使被选中也无人处理，分发自动落到输入框自己的绑定 |

配套的两点：

- 内容区持有**唯一的焦点句柄**（`shell_focus` + `track_focus`），没有输入框时它就是焦点起点，
  否则「没有焦点」时分发从窗口根开始，内容区不在路径里，快捷键会全部失效；
  窗口根只声明 `key_context`，不再 `track_focus`——同一个句柄被两处 track，分发树只认一个。
- 编辑会话结束（提交改名、提交地址栏、收起搜索）时主动把焦点交还内容区，
  否则焦点停在一个已卸载的输入框句柄上，之后所有快捷键都会失效。

### 三、回车是唯一需要路由的键

回车有三种含义，且必须由我们决定（不能依赖输入框的绑定一定生效）：

```text
renaming.is_some()      → commit_rename
address_editing         → commit_address_edit
search_editing          → end_search_edit
其余                     → open_selected
```

三条都要幂等（`commit_rename` 先 `take`；`commit_address_edit` 先清 `address_editing`），
所以即使输入框那条路也生效，两条路都到也只执行一次。取消沿用输入框的 `Esc`
（`clean_on_escape` 清空 → 失焦按放弃处理）。

## 文件夹接管的设计与安全性质

### 控制面必须在设置页，而不只在托盘菜单

这套能力最早只挂在托盘菜单上（外加 `--restore-folder-integration` 命令行）。
问题不在实现，而在**可发现性与可撤回性**：

- 托盘图标是一个用户不一定会点的地方，而接管的效果（双击文件夹换了程序）发生在别处；
- 更糟的是反向：**卸载或移动程序之前必须先还原**，而那时用户已经想不起来入口在哪。

因此设置页里加了「系统集成」分组：两个独立开关 + 一个「恢复」按钮。
三条实现约束：

1. **按真实状态渲染，不乐观更新**。开关的值来自 `folder_association::state()`
   （现读注册表），写操作之后再读一次；写失败时开关保持原样并弹出原因，
   而不是先翻过去再翻回来。
2. **状态缓存在外壳里**，进设置页与每次写操作后刷新。设置页每帧重建，
   每帧读四次注册表是没必要的 IO。
3. **两个开关必须能分开**。只装右键菜单项是零风险的；接管默认打开程序才会改变
   双击行为。合成一个「一键接管」按钮会让用户无法只拿其中一半。

### 为什么必须改注册表

Windows **没有「默认文件管理器」这个可设置的项**（设置 → 默认应用里没有这一栏），
也没有任何受支持的 API。唯一可行的办法是覆盖 shell 的文件夹打开处理器，
这是 Files / Total Commander / Directory Opus 这类工具的通行做法。

### 写在哪、怎么还原

全部写在用户级 `HKCU\Software\Classes`：

| 键                                                            | 用途                                                                  |
| ------------------------------------------------------------- | --------------------------------------------------------------------- |
| `Folder\shell`、`Directory\shell`、`Drive\shell` 的**默认值** | 设为`open` —— 双击文件夹/盘符时用的正是这个「默认动词」               |
| `Folder\shell\open\command`                                   | 文件夹的默认打开处理器（工厂原值`%SystemRoot%\Explorer.exe` 在 HKLM） |
| `Directory\shell\open\command`                                | 文件系统文件夹的打开处理器                                            |
| `Drive\shell\open\command`                                    | 盘符的打开处理器（「此电脑」里或桌面上双击`C:` 走它）                 |
| `Directory\shell\Files\command`                               | 右键菜单项，位置参数`%1`（被选中的那个文件夹）                        |
| `Directory\Background\shell\Files\command`                    | 右键菜单项，位置参数`%V`（当前目录；空白处没有选中项）                |

**每个 progid 必须写两条，缺一不可：**

1. `...\shell` 的默认值 = `open` —— 决定「双击时调用哪个动词」；
2. `...\shell\open\command` 的默认值 = 我们的命令行 —— 决定「那个动词执行什么」。

只写第 2 条的后果很有迷惑性：**右键菜单能生效，双击却毫无变化**。
因为右键菜单是显式枚举动词，而双击用的是「默认动词」；工厂状态下
`...\shell` 的默认值是**未设置**的，此时双击由资源管理器内部处理，根本不走 shell 动词。

改完还必须调用 `SHChangeNotify(SHCNE_ASSOCCHANGED, …)` 广播一次，
否则已经在运行的资源管理器会继续用缓存里的旧处理器，必须重启 `explorer.exe` 才生效。

`HKCU\Software\Classes` 是**叠加**在机器级 `HKLM\Software\Classes` 之上的一层，由此得到两条性质：

1. **不需要管理员权限**；
2. **还原只需删掉这些键** —— `HKLM` 里的原始值原封不动，行为自动恢复。

第 2 条是本功能最重要的安全性质：它不依赖「备份回写」这一步是否正确。
备份只在一种情况下用到——用户此前已在 `HKCU` 里自定义过同一个键，
此时会在覆盖前把原值**连同它的值类型**存进 `HKCU\Software\Files\FolderIntegration`
（值类型必须一起存：把 `REG_EXPAND_SZ` 还原成 `REG_SZ` 会让原值里的 `%VAR%` 不再展开）。

### 为什么有 `restore-explorer.bat`

覆盖生效后，若程序被删除或移动，双击文件夹会打不开，而那时程序本身已经跑不起来。
因此安装时会在程序目录旁边写一个纯 `reg delete` 的脚本，即使程序本体损坏也能双击恢复。
脚本内容保持纯 ASCII —— `.bat` 在中文系统上按 GBK 解释，写 UTF-8 中文会显示成乱码。

### 四个曾经写错的地方（已修，并都加了防回归断言）

- **漏写默认动词**（最要命的一个）：只写了 `...\shell\open\command` 而没把
  `...\shell` 的默认值设为 `open`。症状是「右键菜单生效了、双击还是资源管理器」。
  单测现在断言 `shell_key()` 与 `command_key()` 是两个不同的键。
- **动词键与命令子键混淆**：shell 动词键的默认值是**菜单显示文字**，命令在它的
  `\command` 子键里。状态判定曾读成动词键的默认值，于是「注册表明明写对了、
  程序却一直报未安装」，后果是每次开菜单都重复安装一遍。现在由 `CONTEXT_MENU_KEYS`
  一张表驱动安装 / 状态判定 / 卸载三处，并有单测断言「命令键就是动词键的 `\command` 子键」。
- **重复安装污染备份**：没有安装标记时，第二次安装会把**我们自己写的命令**
  当作「用户原值」备份下来，之后还原就把这个命令又写回去 —— 表现是
  「点了还原但文件夹还是打不开」，且全程无声，因为每一步都返回成功。
  现在有 `DefaultHandlerInstalled` 标记，重复安装不会触碰备份。
- **只读句柄上删值 + 还原中途中断**：`RegOpenKeyExW` 只请求了 `KEY_READ`，
  拿这个句柄删值会被拒绝（错误码 5）；而 `restore_all` 原本用 `?` 在第一个错误处
  就返回，于是一次权限失败会让整个还原**半途而废**。对足控场景来说，
  留在「半接管」状态比「有一项没成功」更糟。现在删除走 `open_for_write`，
  且 `restore_all` 逐项尽力还原、收集失败后统一报告。
